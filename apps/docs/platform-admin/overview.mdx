This section is for the people who run the hosted Lumi product: platform admins. The platform admin is a **separate service** (`admin-api`, default port 4100) with its own web app, its own signing key, its own database role and its own host. It is not part of the workspace API or the self-hosted bundle. Workspace owners and admins cannot sign in to it, and platform admins have no route into a workspace's data except through [impersonation](/platform-admin/tenants-and-impersonation).

<Note>
The workspace API no longer serves `/api/v1/admin/*`, and `SUPER_ADMIN_ENABLED` no longer exists. Platform operators use the admin service described here. The admin API contract is in `docs/api/platform-admin.md` and the generated spec in `docs/admin-openapi.json`.
</Note>

## How it is isolated

- **Own signing key.** `ADMIN_JWT_SECRET` signs admin tokens. The service refuses to start if it is missing, shorter than 32 characters or equal to `JWT_SECRET`. A workspace token is never valid on the admin API, and an admin token is never valid on the workspace API.
- **Own database role.** The service connects as `yulona_admin`, which can only EXECUTE the cross-tenant `sa_*` functions and has no table privileges. The workspace API's role (`yulona_app`) can no longer execute any `sa_*` function.
- **Own cookie and origin.** The session cookie `yl_admin_rt` is `HttpOnly` and `SameSite=Strict`. CORS allows exactly one origin, `ADMIN_WEB_ORIGIN`. Responses carry strict security headers.
- **Optional network allow-list.** `ADMIN_ALLOWED_CIDRS` (comma-separated IPv4/IPv6 CIDRs) limits who can reach the API. Behind Caddy the service trusts only the proxy-provided client IP (`TRUST_PROXY=true`).

## Roles

| Role | Can do |
|---|---|
| `owner` | Everything: create, suspend, restore and delete customers, feature flags and per-customer overrides, LLM provider profiles, admin management, write-mode impersonation, audit export |
| `support` | All reads, notes, tags, resend a pending invitation, retry or discard dead jobs, read-only impersonation |
| `billing` | All reads, grant or adjust credits, change a customer's plan, plan limits, model rates, credit packs |

Support sees health and metadata only: never message text, contact details or secrets. Reading a customer's conversations needs an audited impersonation. The role is read on every request, so a change or a deactivation applies at once.

## Set up the service

<Steps>
  <Step title="Choose the secrets">
    Generate `ADMIN_JWT_SECRET` (`openssl rand -base64 48`) and `ADMIN_DB_PASSWORD` (URL-safe), and decide `ADMIN_WEB_ORIGIN` (for example `https://admin.example.com`) and `ADMIN_SITE_ADDRESS`. Add them to `deploy/.env`. Do not pass `JWT_SECRET` to the admin service.
  </Step>
  <Step title="Create the database role login">
    The migration creates the `yulona_admin` role without a login. With `ADMIN_DB_PASSWORD` set, the `migrate` service (or `bun run migrate` with `ADMIN_DB_PASSWORD` in the environment, run against your own database, never against a shared dev database by accident) enables the login. On a fresh Postgres volume the init script creates it directly.
  </Step>
  <Step title="Enable the host and the profile">
    Copy `deploy/admin-site/admin.caddy.example` to `deploy/admin-site/admin.caddy`, set `COMPOSE_PROFILES=admin`, and run `docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d`. Without that file Caddy serves no admin host.
  </Step>
  <Step title="Create the first admin">
    Run the seed script from a host that can reach the database as the owner role. It never prints the password and reads it from `ADMIN_PASSWORD` or from stdin:
    ```bash
    OWNER_DATABASE_URL='postgres://yulona_owner:OWNER_PASSWORD@DB_HOST:5432/yulona' \
    ADMIN_PASSWORD='a-long-unique-password' \
    bun apps/admin-api/scripts/seed-admin.ts --email ops@example.com --name "Ops Lead" --role owner
    ```
    The password must be at least 12 characters. Re-running the script for the same email resets the password and role. The admin must change the password at first sign-in, unless you pass `--keep-password`. Create further admins from the Admins section (owner only): the invitation returns a temporary password once.
  </Step>
</Steps>

<Warning>
Postgres is on an internal network in the bundled Compose stack. Run the seed script from a trusted host or a container on the `backend` network. Do not publish Postgres to make this work.
</Warning>

## Run the web app

The admin console is the static app `apps/admin-web`. In Compose the `admin` profile starts it as `admin-web` behind the same Caddy admin host as the API (leave `ADMIN_WEB_API_URL` empty). For local development run `bun run dev:admin-api` and `bun run dev:admin-web` (port 5178), and set `ADMIN_WEB_ORIGIN=http://localhost:5178`. Then follow the [Admin console tour](/platform-admin/console-tour).

## Sign in and sessions

- **Sessions survive a reload.** The access token lasts 15 minutes and is held in memory. A rotating refresh token lives in the `HttpOnly` cookie for 7 days (`ADMIN_SESSION_TTL_DAYS`). Reusing an old refresh token revokes the whole session. Logging out or deactivating an admin revokes it immediately.
- **Lockout.** After 5 failed sign-ins the account locks. The lock starts at 30 seconds, doubles with each further failure and is capped at 15 minutes.
- **Rate limits.** Per admin, 30 reads and 10 writes per minute (`ADMIN_RATE_READ`, `ADMIN_RATE_WRITE`), plus limits on sign-in attempts per IP and per IP and email.
- **Audit.** Every write is recorded in the platform audit log. Opening a customer's detail page and every export are recorded too (one entry per admin, customer and action every 10 minutes for views). Only owners can export the audit log.

### Two-factor authentication

Every admin can enrol an authenticator app (TOTP) from their profile: `POST /api/v1/auth/2fa/setup` with the password returns a secret and an `otpauth` URL, `POST /api/v1/auth/2fa/confirm` with a code enables it and returns 10 single-use recovery codes, shown once. Once enrolled, sign-in asks for a code (or a recovery code). `ADMIN_REQUIRE_2FA` is `false` by default; set it to `true` later to make enrolment mandatory (admins without it get a restricted session until they enrol). An owner can reset another admin's 2FA. TOTP secrets are encrypted with `ENCRYPTION_KEY`; without it the 2FA endpoints answer `503`.

### Customer health

Each customer gets a score from 100 minus penalties, and a bucket: healthy (80 and above), watch (50 to 79) or at risk (below 50). Penalties: failed background jobs, failed webhook deliveries, channel errors and failed channel deliveries, failed knowledge ingests (all within 7 days), credits exhausted (25) or under 10% (10), a failed payment (25), no activity for 14 days (15), no agent ever published (10), and recent abuse blocks. The top reasons are returned with the score.

### System health

`GET /api/v1/health` reports an overall `ok`, `degraded` or `down`: the database and its latency, queue counts with the oldest queued job's age, and the worker heartbeat (alive when under 120 seconds old). The status is `degraded` when the worker is stale or dead jobs exist.

## Common problems

- The service exits at start: check the message. Typical causes are a missing or short `ADMIN_JWT_SECRET`, `ADMIN_JWT_SECRET` equal to `JWT_SECRET`, no `ADMIN_DB_URL` or `ADMIN_DB_PASSWORD`, or (in production) an `ADMIN_WEB_ORIGIN` that is not https.
- Sign-in says the account is locked: wait out the lock, or reset the password with the seed script, which also clears the lock.
- `403 session_restricted`: the session must first change a temporary password or, with `ADMIN_REQUIRE_2FA=true`, enrol 2FA.
- `403 forbidden` from everywhere: the client IP is not in `ADMIN_ALLOWED_CIDRS`, or the role does not allow the action.
