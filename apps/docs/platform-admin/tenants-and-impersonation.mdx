This page is for platform admins of the hosted product. A tenant is one customer workspace. The platform admin service is where you look one up, check its health, plan and usage, change its status, adjust its AI credits and, when a customer needs hands-on help, view the product as one of its users for a short, audited session. Calls below go to the admin API (default `http://localhost:4100`, your admin host in production) with the access token from `POST /api/v1/auth/login`; see [Platform admin overview](/platform-admin/overview).

## Find a tenant

`GET /api/v1/tenants` searches and filters on the server: `q` matches the name, the id and the email of any member; filters are `status`, `plan`, `health` (`healthy`, `watch`, `at_risk`), `createdFrom`, `createdTo`, `inactiveDays`, `hasErrors`, `credits` (`ok`, `low`, `exhausted`, `unlimited`) and `tag`; `sort` is one of `createdAt`, `name`, `health`, `lastActive`, `credits`, `errors`. The response has `items`, `total` (honouring the filters), `limit` and `offset`.

```bash
curl "https://admin-api.example.com/api/v1/tenants?q=acme&health=at_risk&sort=health&order=asc" \
  -H "Authorization: Bearer ADMIN_TOKEN"
```

`GET /api/v1/tenants/export` returns the same list as CSV. `GET /api/v1/search?q=` powers a command palette: tenants by name, id or member email, and users by email.

## Read a customer

`GET /api/v1/tenants/:id` returns the overview: status, plan, owner, health score with reasons, counts (users, agents, widgets, channels, contacts, conversations, knowledge sources), plan limits with live use, billing state, credits, tags and the notes count. Opening it is written to the audit log (once per admin and customer every 10 minutes). Related reads:

| Endpoint | Returns |
|---|---|
| `/tenants/:id/users` | Team members (role, last sign-in, locked) and invitations |
| `/tenants/:id/assets` | Agents, widgets, channels, knowledge, connections, webhooks, calendar and CRM with status and last error; no keys or URLs with credentials |
| `/tenants/:id/errors` | Failures: dead jobs, webhook deliveries, channel errors, failed ingests, notification emails, CRM syncs, system-failure and abuse handoffs, tool failures; filter by `kind` and `days`; each item has a "what to check" hint |
| `/tenants/:id/timeline` | Merged tenant audit, platform audit, billing, handoffs and impersonation |
| `/tenants/:id/billing`, `/ai-usage`, `/usage`, `/credits`, `/flags` | Subscription and events, AI usage by day and model, daily rollup, credits, flag overrides |
| `/tenants/:id/notes`, `/tags` | Internal notes and tags (support and owner write) |

None of these return message text, contact names, emails or phone numbers, secrets or ciphertext.

## Suspend and unsuspend

`POST /tenants/:id/suspend` revokes every session of the tenant and blocks sign-in at once, including live access tokens. `POST /tenants/:id/unsuspend` reverses it. Both write to the platform audit log and to the tenant's own audit log. A suspended tenant cannot be impersonated. Owner role only.

## Delete and restore

`DELETE /tenants/:id` is a soft delete: users cannot sign in and the tenant shows as `deleted`. `POST /tenants/:id/restore` works for 30 days. After that the worker's hourly maintenance job hard-deletes the tenant and all its rows, and restore answers `409`. Owner role only.

```bash
curl -X DELETE https://admin-api.example.com/api/v1/tenants/TENANT_ID -H "Authorization: Bearer ADMIN_TOKEN"
curl -X POST https://admin-api.example.com/api/v1/tenants/TENANT_ID/restore -H "Authorization: Bearer ADMIN_TOKEN"
```

<Warning>
After 30 days the purge is permanent. Export anything a customer needs before that point.
</Warning>

## Plan, tags, notes and invitations

- `PUT /tenants/:id/plan` with `{ "plan": "pro" }` (owner or billing).
- `PUT /tenants/:id/tags` replaces tags; `POST /tenants/tags/bulk` adds and removes tags on up to 200 customers (owner or support).
- `POST /tenants/:id/notes` adds an internal note (owner or support). Support can delete only its own notes.
- `POST /tenants/:id/invitations/:invitationId/resend` re-issues a pending invitation and emails a fresh 7-day link to the invitee. The link is never returned to you.

## Impersonation

Impersonation lets you see the product as a customer user, for support and debugging. It never hands the admin service a customer token: the admin API returns a **one-time code**, and the customer app exchanges it.

<Steps>
  <Step title="Start a session">
    `POST /tenants/:id/impersonate` with `{ "reason": "support ticket 1234" }` (5 to 500 characters; optional `userId`, default the tenant's oldest active owner). It is **read-only by default**. Owners can ask for write mode with `"readOnly": false`; support and billing cannot, and billing cannot impersonate at all. The response contains `code` (valid 60 seconds, single use) and `customerUrl`, which looks like `https://app.example.com/impersonate#code=...`.
  </Step>
  <Step title="Open the customer app">
    The admin web app opens `customerUrl` in a new tab. The code travels in the URL fragment, so it never reaches a server log. The customer app calls `POST /api/v1/auth/impersonation/exchange` with the code and receives a normal 15-minute token for the user, capped at the `admin` role.
  </Step>
  <Step title="End it">
    `POST /impersonation/:sessionId/end` revokes the token at once. Otherwise it expires after 15 minutes counted from the exchange.
  </Step>
</Steps>

| Rule | Detail |
|---|---|
| Read-only sessions | The token carries a `ro` claim and the customer API rejects every request except `GET` and `HEAD` with `403` |
| Codes | Stored hashed, single use, 60 seconds; a wrong, used or expired code answers `400` |
| Role | Capped at admin: no role or ownership changes and no billing management |
| Blocked for | Suspended and deleted tenants (`409`) |

The banner in the customer app shows the session and, for read-only sessions, says so. Start and end are written to the platform audit log (`impersonation.start`, `impersonation.end`) and to the tenant's audit log (`impersonation.started`, `impersonation.exchanged`, `impersonation.ended`, with `readOnly`). Every write made in write mode carries `metadata.impersonatorId`. `GET /tenants/:id/impersonations` and `GET /impersonations` list the history.

## Common problems

- Impersonation answers `409`: the tenant is suspended or deleted.
- Impersonation answers `403`: only owners can use write mode, and billing admins cannot impersonate.
- The customer app says the code is invalid: codes last 60 seconds and work once. Start a new session.
