This page is for operators installing Lumi for the first time. By the end you will have a running stack behind HTTPS and an admin account for your single workspace.

## Requirements

| Item | Minimum |
|---|---|
| Operating system | Linux host |
| CPU, memory, disk | 2 vCPU, 4 GB RAM, 20 GB disk |
| Software | Docker Engine 24 or later with Compose v2, plus `openssl` and `git` |
| Network | A DNS A/AAAA record pointing at the host, and ports 80 and 443 open (automatic HTTPS) |

The compose resource limits add up to about 3.7 GB. Add roughly 2 GB if you enable ClamAV and 512 MB for MinIO.

<Note>
Without a domain you can still install for evaluation: use `localhost` (local test CA) or `:80` (plain HTTP, trusted networks only).
</Note>

## Install

<Steps>
  <Step title="Get the code">
    ```bash
    git clone <repo> yulona && cd yulona
    ```
    Replace `<repo>` with the repository URL you were given.
  </Step>
  <Step title="Run the setup script">
    ```bash
    deploy/setup.sh app.example.com --email you@example.com --workspace "Acme"
    ```
    The domain is the first argument. Options: `--email` (admin login, default `admin@<host>`), `--workspace` (default `My Workspace`), `--name` (admin display name, default `Admin`).
  </Step>
  <Step title="Save the printed password">
    When the script finishes it prints the URL, the admin email and a generated password. The password is shown once. Sign in and change it.
  </Step>
  <Step title="Check health">
    ```bash
    curl https://app.example.com/readyz
    ```
    A healthy stack answers `{"status":"ok","checks":{"db":"ok","redis":"ok"}}`.
  </Step>
</Steps>

For an install without a domain:

<CodeGroup>
```bash Local test CA
deploy/setup.sh
# https://localhost with a self-signed local CA
```

```bash Plain HTTP
deploy/setup.sh :80
# http://<this-host>, only on a trusted network
```
</CodeGroup>

### What setup.sh does

1. Checks that `docker`, Compose v2 and `openssl` are installed.
2. Refuses to continue if `deploy/.env` already exists, so it never overwrites secrets. Use `deploy/upgrade.sh` for existing installs.
3. Copies `deploy/.env.example` to `deploy/.env` (mode 600) and fills `SITE_ADDRESS`, `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET`, `ENCRYPTION_KEY` and `MINIO_ROOT_PASSWORD` with random values.
4. Builds the images.
5. Starts Postgres and Redis. On first start Postgres runs `deploy/postgres/init-roles.sh`, which creates the runtime role `yulona_app` (no `BYPASSRLS`, not a superuser) with `APP_DB_PASSWORD`, and enables the `vector` extension.
6. Runs the `migrate` one-shot service as the owner role `yulona_owner`.
7. Runs the `create-tenant` one-shot service to create your workspace and its owner.
8. Starts everything and waits for health checks.

<Warning>
Back up `deploy/.env` immediately. `ENCRYPTION_KEY` encrypts channel credentials, webhook secrets and OAuth tokens. If you lose it, those credentials cannot be recovered.
</Warning>

## Services, ports and URLs

| Service | Published port | Reachable at |
|---|---|---|
| `caddy` | 80, 443 (TCP) and 443 (UDP, HTTP/3) | `https://<SITE_ADDRESS>` |
| `api` | none (3000 inside the network) | `/api/*`, `/ws`, `/healthz`, `/readyz` through Caddy |
| `dashboard` | none (8080 inside the network) | everything else through Caddy |
| `postgres`, `redis` | none | internal network only |

Caddy sends `/api/*`, `/ws`, `/healthz` and `/readyz` to the API and everything else to the dashboard. It also adds compression, an HSTS header, and limits request bodies to 2 MB at the proxy. The API enforces its own `BODY_LIMIT_BYTES` and a 10 MB file limit on knowledge uploads.

### TLS

Set `SITE_ADDRESS` to your domain and Caddy obtains and renews a Let's Encrypt certificate automatically. Ports 80 and 443 must reach the host. `localhost` uses a local certificate authority your browser will not trust by default, and `:80` disables TLS.

To put your own reverse proxy in front instead (nginx, a load balancer), do not publish ports 80 and 443 at all: see [Behind your own reverse proxy](#behind-your-own-reverse-proxy).

### Behind your own reverse proxy

Use this when the VM is private and a proxy you already run terminates TLS and forwards requests to it. The VM then listens for plain HTTP on a private address and a port you choose (for example `10.0.0.5:8080`). Nothing needs ports 80 or 443.

Caddy stays on the VM for one reason: it switches traffic between the old and new API during a zero-downtime rollout. In this mode it does no TLS and requests no certificates.

<Steps>
  <Step title="Install in proxy mode">
    On a fresh VM: `deploy/setup.sh api.example.com --behind-proxy --port 8080 --bind 10.0.0.5 --email you@example.com`. On an existing install, add these to `deploy/.env` and restart Caddy:

    ```bash
    CADDYFILE=Caddyfile.proxied
    PROXY_BIND=10.0.0.5          # the VM's private address
    HTTP_PORT=8080               # the port your proxy forwards to
    HTTPS_PORT=8443              # unused, only needs to be free
    PROXY_TRUSTED_CIDRS=10.0.0.4/32   # your proxy's address
    ```

    ```bash
    docker compose --project-name yulona --env-file deploy/.env -f deploy/docker-compose.yml up -d caddy
    ```
  </Step>
  <Step title="Point your proxy at it">
    Forward the API host to `http://10.0.0.5:8080`, keep the `Host` header, send the client address in `X-Forwarded-For`, and allow WebSocket upgrades. For nginx:

    ```nginx
    server {
        listen 443 ssl http2;
        server_name api.example.com admin-api.example.com;
        # ssl_certificate ... (your certificates)

        client_max_body_size 12m;          # knowledge uploads are limited to 10 MB

        location / {
            proxy_pass http://10.0.0.5:8080;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;   # map $http_upgrade $connection_upgrade { default upgrade; '' close; }
            proxy_read_timeout 3600s;          # long-lived WebSocket and event streams
            proxy_buffering off;
        }
    }
    ```
  </Step>
  <Step title="Enable the admin API host (optional)">
    Copy `deploy/admin-site/admin-api-proxied.caddy.example` to `deploy/admin-site/admin.caddy`, set `ADMIN_SITE_ADDRESS=admin-api.example.com`, and reload Caddy. Your proxy forwards that host to the same address and port.
  </Step>
</Steps>

Real visitor addresses matter: the API rate-limits by address, and `ADMIN_ALLOWED_CIDRS` checks it. With two proxies in front of the API, the API would otherwise see only your proxy's address. `Caddyfile.proxied` therefore reads `X-Forwarded-For` from right to left, trusting only the addresses in `PROXY_TRUSTED_CIDRS`, and passes the real client address on as the single forwarded value. Set `PROXY_TRUSTED_CIDRS` to your proxy's exact address when you can; the default trusts every private range. Visitors cannot forge their address by sending their own `X-Forwarded-For`. Keep `TRUST_PROXY=true`, which the stack sets.

Check it: `curl -H 'Host: api.example.com' http://10.0.0.5:8080/readyz` from the proxy host should return `{"status":"ok"}`.

## Add another workspace or admin

Self-hosted mode is designed for one workspace, but you can create more with the same command setup used:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  run --rm create-tenant --workspace Acme --email a@b.com
```

Flags: `--workspace`, `--email`, `--name`, `--password` (or `ADMIN_PASSWORD` in the environment), `--plan` (default `self_hosted`) and `--json`. Without a password a strong one is generated and printed once. The command uses the owner database role and rejects an email that already has an account.

## Optional services

Enable them with `COMPOSE_PROFILES` in `deploy/.env`, comma separated:

```bash
COMPOSE_PROFILES=minio,clamav
```

<Tabs>
  <Tab title="MinIO (storage)">
    Adds S3-compatible storage on the internal network and creates the bucket for you. Point the S3 settings at it:

    ```bash
    S3_ENDPOINT=http://minio:9000
    S3_BUCKET=yulona
    S3_REGION=us-east-1
    S3_ACCESS_KEY_ID=yulona            # your MINIO_ROOT_USER
    S3_SECRET_ACCESS_KEY=<MINIO_ROOT_PASSWORD value>
    ```
    Without any S3 settings, uploaded files and exports are kept in memory and are lost on restart.
  </Tab>
  <Tab title="ClamAV (virus scanning)">
    Adds `clamd` and an HTTP wrapper. Set `CLAMAV_URL=http://clamav:3000`. Allow about 1.5 to 2 GB extra RAM. A `tcp://host:3310` address of your own `clamd` also works. See [Channels and integrations setup](/self-hosting/channels-and-integrations-setup#clamav).
  </Tab>
</Tabs>

Apply a change with:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d
```

## Development compose

`deploy/docker-compose.dev.yml` starts only Postgres and Redis for local development, bound to `127.0.0.1` (Postgres on 5433, Redis on 6380) with throwaway credentials. Never use it in production.

```bash
docker compose -f deploy/docker-compose.dev.yml up -d postgres redis
```

## Using prebuilt images

By default the images are built from the repository. To skip building, set pinned registry images in `deploy/.env`:

```bash
YULONA_API_IMAGE=ghcr.io/your-org/yulona/api:main
YULONA_DASHBOARD_IMAGE=ghcr.io/your-org/yulona/dashboard:main
```

For continuous deploys of the API and worker with no downtime, install once under `/opt/yulona`, then use `deploy/rollout.sh` (and the `deploy-backend` GitHub Actions workflow with a self-hosted runner labelled `yulona-vpc`). See [Upgrade, backup and restore](/self-hosting/upgrade-backup-restore#zero-downtime-backend-rollout).

## Dashboard and admin web on Vercel

The tenant dashboard and platform admin web are static SPAs. You can host them on Vercel while the API, worker, Postgres and Redis stay on the VM.

1. Create two Vercel projects from this repository. Set **Root Directory** to `apps/dashboard` and `apps/admin-web`.
2. Production env: `VITE_API_URL=https://api.example.com` on the dashboard project, and `VITE_ADMIN_API_URL=https://admin-api.example.com` (or your admin API origin) on the admin project. Do not add a Vercel rewrite of `/api` to the VM: chat and WebSockets must go straight to the API host.
3. On the VM set `CORS_ORIGINS` to those exact origins, `PUBLIC_API_URL` to the API origin, and `WIDGET_SCRIPT_URL` to `https://app.example.com/widget.js` (the dashboard project serves the widget bundle). If the dashboard and API are different sites (not subdomains of one domain), set `CROSS_SITE_COOKIES=true`.
4. Use `deploy/Caddyfile.api` on the VM so Caddy serves only the API (and optional admin host). For the admin API host copy `deploy/admin-site/admin-api-only.caddy.example` to `deploy/admin-site/admin.caddy`.
5. In each Vercel project, keep **Include source files outside of the Root Directory** enabled (the build installs the whole monorepo). Each project's `vercel.json` sets an `ignoreCommand` (`scripts/vercel-ignore.sh`), so Vercel skips a deployment when nothing the project is built from changed since the last successful deployment (a project or branch with no deployment yet always builds): the dashboard rebuilds for `apps/dashboard`, `apps/widget` and `packages/shared`, and the admin web only for `apps/admin-web`. A change to `bun.lock`, the root `package.json` or `tsconfig.base.json` rebuilds both.
6. Use custom domains under one parent domain, for example `app.example.com`, `admin.example.com`, `api.example.com` and `admin-api.example.com`. The admin refresh cookie is `SameSite=Strict`, so an admin web on `*.vercel.app` talking to your own API domain would sign admins out on every reload.

`deploy/.env.backend.example` lists every VM variable for this layout, including the Vercel variables (`VITE_API_URL`, `VITE_ADMIN_API_URL`) and the GitHub variable that switches backend deploys on.

Each page view that loads `widget.js` counts as a Vercel CDN request. After the script loads, open chats use WebSocket, SSE or polling against `apiUrl` on the VM and do not add Vercel requests. Hobby is for personal, non-commercial use; a product workspace belongs on Pro.

## Common problems

- `variable is missing a value`: run Compose with `--env-file deploy/.env`, or run `deploy/setup.sh` first.
- `setup.sh` says `deploy/.env already exists`: that is intentional. Delete the file only if you want to start over with an empty database.
- More fixes are in [Troubleshooting](/self-hosting/troubleshooting).
