This page is for operators. Four scripts in `deploy/` cover the routine work: `upgrade.sh`, `rollout.sh`, `backup.sh` and `restore.sh`. All of them read `deploy/.env` and must be run on the host that runs the stack.

## Back up

`deploy/backup.sh` writes a compressed logical dump of the database.

```bash
deploy/backup.sh
# backup written: deploy/backups/yulona-20261019-031700.sql.gz (123456 bytes)
```

It runs `pg_dump` as the owner role inside the `postgres` container, checks the file is not empty, verifies it with `gzip -t`, and keeps the newest 14 files named `yulona-*.sql.gz`. Set `KEEP=30` in the environment to keep more. Pass a path to write somewhere else; custom paths are never pruned.

Schedule it with cron and copy the files off the host:

```bash
17 3 * * * /opt/yulona/deploy/backup.sh
```

### What to back up

| Item | How | Why |
|---|---|---|
| Database | `deploy/backup.sh` | All workspace data, jobs and settings |
| `deploy/.env` | Copy to a secret store | `ENCRYPTION_KEY` is required to read stored channel and OAuth credentials, and `JWT_SECRET` signs sessions |
| Object storage | Snapshot your S3 or MinIO bucket | Uploaded knowledge files and exports are not in the database dump |

<Warning>
Backups contain customer conversations and encrypted credentials. Encrypt them before they leave the host, restrict access, and delete old copies. The script creates files readable only by the owner (umask 077).
</Warning>

## Zero-downtime backend rollout

Use this when the API and worker run from registry images on a VM (for example under `/opt/yulona`) and the dashboard lives elsewhere (such as Vercel). `deploy/rollout.sh` swaps `api` and `worker` only after the new containers pass checks. Postgres, Redis and Caddy stay up.

```bash
deploy/rollout.sh ghcr.io/your-org/yulona/api:<sha>
```

The script:

1. Writes `deploy/backups/pre-rollout-<timestamp>.sql.gz` and aborts if it is empty.
2. Pulls the image and runs the `migrate` one-shot from `deploy/docker-compose.backend.yml` on the existing `yulona_edge` / `yulona_backend` networks. If migrate fails, the live containers are left alone.
3. Starts the next blue/green slot (`yulona-backend-blue` or `yulona-backend-green`) with Docker network alias `api`.
4. Polls `/readyz` inside the new API container and checks the new worker logged `worker started`.
5. Reloads Caddy, stops the previous API and worker (including the ones from the first `setup.sh` stack), reloads Caddy again.
6. Records the live slot in `deploy/.deploy-slot` and the previous image tag in `deploy/.deploy-previous`.

Caddy’s API proxy uses a short `/readyz` health check so a stopped container is dropped quickly. For an API-only host (dashboard on Vercel), set `CADDYFILE=Caddyfile.api` in `deploy/.env` (or copy `deploy/Caddyfile.api` over `deploy/Caddyfile`) and restart Caddy once. If your own reverse proxy terminates TLS in front of the VM, use `CADDYFILE=Caddyfile.proxied` instead and no ports 80 or 443 are needed: see [Behind your own reverse proxy](/self-hosting/requirements-and-install#behind-your-own-reverse-proxy).

<Warning>
Migrations run while the old API is still serving traffic. Ship schema changes that the old code can still read (add columns and tables; do not drop or rename in the same release as the code that stops using them).
</Warning>

### GitHub Actions on the VPC VM

1. Install the stack once with `deploy/setup.sh` under `/opt/yulona` (so `deploy/.env` mode 600 stays on the host).
2. Register a [self-hosted runner](https://docs.github.com/en/actions/hosting-your-own-runners) on that VM with labels `self-hosted` and `yulona-vpc`. Give the runner user access to the Docker socket. Do not use this runner for pull requests from forks.
3. Enable GitHub Packages (GHCR) for the repository.
4. Fill in `deploy/.env` on the VM from `deploy/.env.backend.example` (it lists every value a VM-plus-Vercel setup needs and why). Secrets never leave `deploy/.env`; GitHub needs no secrets for deploys.
5. In the repository, set the Actions **variable** `BACKEND_DEPLOY_ENABLED` to `true`. Until you do, the `deploy-backend` workflow does nothing, so you can push the code before the VM exists.

### Deploy only what changed

The `deploy-backend` workflow runs on pushes to `main` that touch backend code. It works out which service changed, runs the tests, builds only that image and rolls out only that service:

| You changed | What is built and deployed |
|---|---|
| `apps/api`, `apps/worker`, or any `packages/*` | the `api` image (API and worker run from it), with `deploy/rollout.sh` (backup, migrate, blue/green) |
| `apps/admin-api`, or `packages/{ai-runtime,crypto,db,providers,shared}` | the `admin-api` image, with `deploy/rollout-admin-api.sh` (only the admin API container restarts, in its own compose project `yulona-admin-api`) |
| `apps/dashboard`, `apps/admin-web`, `apps/widget` | nothing here: these are Vercel projects that build themselves (see [Dashboard and admin web on Vercel](/self-hosting/requirements-and-install#dashboard-and-admin-web-on-vercel)) |
| docs only | nothing |

When one push changes both, the admin API rolls out after the API (the API rollout applies the database migrations). The admin API is recreated in place, so it is unavailable for a few seconds; if the new image does not become ready, the script restores the previous image. To deploy by hand, run `deploy/rollout-admin-api.sh ghcr.io/<owner>/<repo>/admin-api:<sha>`, or start the workflow from the Actions tab and choose a service.

The API and worker share one image and one rollout because they share code and database migrations. Changing only the worker therefore rebuilds that image and rolls out both.

Pull requests run the tests (`ci`) but never deploy. Protect `main` so changes arrive through a pull request with the `ci` check required.

## In-place upgrade (full stack)

`deploy/upgrade.sh` rebuilds or pulls images and restarts `api`, `worker`, `dashboard` and `caddy` one service at a time. There is a short gap per service while the new container replaces the old one. Prefer `rollout.sh` when you need the API to stay up.

<Steps>
  <Step title="Read the changelog">
    Check the [changelog](/changelog) for breaking changes.
  </Step>
  <Step title="Run the upgrade script">
    ```bash
    deploy/upgrade.sh
    ```
    Use `deploy/upgrade.sh --no-git` when you deploy registry images (`YULONA_API_IMAGE` and `YULONA_DASHBOARD_IMAGE` in `deploy/.env`) and do not want a `git pull`.
  </Step>
  <Step title="Confirm health">
    ```bash
    curl https://app.example.com/readyz
    docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
    ```
  </Step>
</Steps>

The script does these things in order and stops on any error:

1. Writes a pre-upgrade backup to `deploy/backups/pre-upgrade-<timestamp>.sql.gz` and aborts if it is empty. These files are not pruned automatically.
2. Records the current image ids for rollback.
3. Runs `git pull --ff-only` (unless `--no-git`, or the directory is not a git checkout).
4. Builds with `build --pull` and pulls registry images.
5. Starts Postgres and Redis, then runs the `migrate` one-shot service. If migration fails, it prints how to restore, exits, and leaves the running services untouched.
6. Restarts `api`, `worker`, `dashboard` and `caddy` one at a time, waiting for each to be healthy.

<Note>
Migrations only move forward and are applied with the owner role `yulona_owner`. There is no "down" migration. To undo a schema change you restore the pre-upgrade backup.
</Note>

### Do not set APP_DB_PASSWORD when migrating by hand

The bundled `migrate` service does not receive `APP_DB_PASSWORD`, so it never touches the runtime role. But the migration command (`packages/db/src/cli.ts`) runs `ALTER ROLE yulona_app LOGIN PASSWORD ...` whenever `APP_DB_PASSWORD` is present in its environment. If you run migrations manually with that variable set, the password of `yulona_app` changes, and `api` and `worker` fail to connect unless `deploy/.env` already holds the same value.

To change the runtime password deliberately, do both steps together:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec postgres \
  psql -U yulona_owner -d yulona -c "ALTER ROLE yulona_app PASSWORD 'NEW_URL_SAFE_PASSWORD'"
# then put the same value in APP_DB_PASSWORD in deploy/.env and restart api and worker
```

Editing `APP_DB_PASSWORD` in `deploy/.env` alone does nothing to an existing database, because the role is created only at first start.

## Restore

`deploy/restore.sh` replaces the database contents with a backup. It is destructive.

```bash
deploy/restore.sh deploy/backups/yulona-20261019-031700.sql.gz
```

It asks you to type `restore` (skip with `--yes`), then:

1. Verifies the archive with `gzip -t`.
2. Stops `api` and `worker`.
3. Drops and recreates the `public` schema as the owner role.
4. Loads the dump.
5. Runs `migrate` again, which brings an older dump forward and re-applies role grants.
6. Starts everything and waits for health.

Restore the object-storage bucket separately if you lost it, and use the same `ENCRYPTION_KEY` that was active when the backup was made. Practise a restore on a scratch host regularly; an untested backup is not a backup.

## Roll back

If a rollout misbehaves but the schema is fine, re-run the previous image tag (printed at the end of `rollout.sh`, and stored in `deploy/.deploy-previous`):

```bash
deploy/rollout.sh "$(cat deploy/.deploy-previous)"
```

For an in-place full-stack upgrade, check out the previous commit or set `YULONA_API_IMAGE` and `YULONA_DASHBOARD_IMAGE` in `deploy/.env` to the previous tags, then run `docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build`.

If the new release applied migrations the old code cannot read, also restore the pre-upgrade or pre-rollout backup:

```bash
deploy/restore.sh deploy/backups/pre-rollout-20261019-040000.sql.gz
```

You lose everything written after that backup was taken, so prefer fixing forward when you can.

## Common problems

- `error: backup is empty; aborting`: the `postgres` container is not running. Start the stack, then retry.
- Migration failed during upgrade: read the output of `docker compose ... run --rm migrate`. Services keep running the old version. Fix the cause or restore.
- Api cannot connect after a restore: check that `APP_DB_PASSWORD` in `deploy/.env` matches the `yulona_app` role. See [Troubleshooting](/self-hosting/troubleshooting#api-cannot-log-in-to-postgres).
